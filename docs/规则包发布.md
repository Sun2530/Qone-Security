# 规则包发布流程

> 一句话原理：**GitHub 仓库就是你的更新服务器**，用户端每 24 小时查一次版号，
> 版本高了就把 `.yar` 拉下来。没有服务器、没有账号、没有费用。

---

## 为什么只发规则，不发哈希

| 东西 | 版权 | 能不能随程序/仓库公开分发 |
|---|---|---|
| 你写的 YARA 规则 | 你 | 能，MIT 随便发 |
| MalwareBazaar 的哈希摘要 | abuse.ch | **不能**，不是 CC0，转存违约 |
| ClamAV 的库 | Cisco Talos | 不能，让用户自己装 |

所以更新通道只搬 `.yar`。哈希那条线走用户自己的 Auth-Key（引擎页那个输入框），
数据落在他本机，不经过你，也不进仓库。**这条边界不要越。**

## 目录结构

```
chickguard/
├── assets/yara/
│   ├── qone-core.yar        ← 规则本体（改这里）
│   └── manifest.json        ← 版本清单（脚本生成，别手改）
├── rules/                   ← 发布目录，推上 GitHub 就生效
│   ├── qone-core.yar        ← 与上面那份内容相同
│   └── manifest.json
└── tools/publish_rules.py   ← 一条命令同步两边
```

`assets/` 那份随 exe 打包，是**离线兜底**；`rules/` 那份是**线上版本**。
两边必须一致——程序会拿线上版本和内置版本比大小，不一致会让用户越更新越旧。

---

## 发版三步

**1. 改规则**

编辑 `assets/yara/qone-core.yar`，加规则、修误报。改完先自己跑一遍：

```bash
python -c "import yara; yara.compile(filepath='assets/yara/qone-core.yar'); print('OK')"
```

**2. 出清单**

```bash
python tools/publish_rules.py 2026.11.02 "新增银狐侧加载器 3 条；修正下载器误报"
```

版本号用 `年.月.日`，**必须比上一版大**。脚本会算 SHA-256、写两份 manifest、
把规则同步到 `rules/`。

**3. 推仓库**

```bash
git add rules assets/yara && git commit -m "rules: 2026.11.02" && git push
```

用户端在下次启动（或点「检查更新」）时就会拿到。**不用重新发 exe。**

## 仓库要求

`rulesync.py` 顶部写了三个地址，默认指向：

```
https://raw.githubusercontent.com/Sun2530/qone-security/main/rules
https://cdn.jsdelivr.net/gh/Sun2530/qone-security@main/rules
https://gitee.com/Sun2530/qone-security/raw/main/rules
```

**仓库名或分支不一样，就必须改这三行**，否则用户永远拉不到东西。
三个地址依次尝试，前一个失败自动退到下一个；都失败就静默用内置规则，
界面只把版本徽标的点变灰，不弹任何错误框。

## 下载下来的规则会被怎么检查

规则文件是**代码**，不是数据，所以不能直接信：

1. **SHA-256 与清单比对** —— 防传输篡改
2. **拒绝 `include`** —— 它能在编译期读本机文件
3. **`import` 只允许白名单**（pe / hash / math / time / dotnet / elf / magic）
4. **整包试编译一次**，超时（疑似正则回溯）也算失败

任何一关不过就**整包丢弃**，不做部分生效。宁可这次没更新，也不能让一条坏规则进来。

## 常见问题

**改了规则忘了跑脚本？**
用户会拿到旧清单，版本号没变 → 不更新。每次都跑一次 `publish_rules.py`，别手改 manifest。

**想让所有人立刻拿到？**
把 manifest 的 version 往后调，或者告诉用户点「检查更新」（手动检查不受 24 小时节流限制）。

**用户在国内连不上？**
jsDelivr 那个地址通常比 raw 快。再不行让用户自己在更新页填一个 Gitee 镜像地址
（填了自定义源后，内置三个会排在它后面作为备用）。

**仓库被投毒怎么办？**
这是真实风险：账号被盗 → 推恶意规则 → 所有用户中招。现在有三关挡着（尤其禁 include
和试编译），能挡掉大部分，但挡不住「语法正确、逻辑恶意」的规则。
真要防死，下一步是给 manifest 加 Ed25519 签名、公钥硬编码在 exe 里——
一个人维护的话成本偏高，先记在这里。
